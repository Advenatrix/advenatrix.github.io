# GeoRP — Development Plan

## Critical Rewrites — Supabase Migration

### Motivation
Current backend (Express + SQLite) can't run on GitHub Pages. Supabase (already partially integrated) provides everything needed — Auth, PostgreSQL, Edge Functions (HTTP handlers), Cron (turn scheduling), and Storage (images) — all within the free tier.

### Architecture Change

| Before | After |
|---|---|
| Express + SQLite (local dev) | Supabase PostgreSQL (cloud) |
| Custom JWT + SHA-256 auth | Supabase Auth with custom username identity |
| Express route handlers (`server/src/routes/`) | Single Edge Function `game-api` with internal routing |
| Manual turn processing via admin button | Edge Function `process-turn` triggered by Supabase Cron (`pg_cron`) |
| Admin routes in Express | Edge Function `admin` |
| Discord CDN for flag/leader images | Supabase Storage |
| Frontend `api.ts` fetches `/api/*` | Frontend uses `supabase-js` for reads + Edge Function invocations for writes |

### Auth: Username-Based Custom Login

Supabase Auth requires an email for sign-in. We'll use a convention: store usernames as `username@georp.game` in `auth.users`. The frontend login form stays username-based — it appends `@georp.game` before calling `supabase.auth.signInWithPassword()`. The `authStore.ts` handles this transparently.

### Seed: One-Time Migration + Admin Importer

- `002_full_schema.sql` and `seed.sql` run once via `supabase migration up`.
- `seed.sql` inserts: 8 nations (player_id=NULL), 56 companies, 56 sector_modifiers, 8 eco_history rows (turn 0), game_settings, turn 1, and minimal unit_templates (one per unit type per nation).
- Full military seed (formations + units with varied tiers and random strengths) is generated by the `seed-military` endpoint in the `admin` Edge Function — called by the "Import Seed Data" button in the admin UI. This keeps complex TypeScript logic (random strength, tier multipliers, named ships/squadrons) out of raw SQL.
- Admin page gets an "Import Seed Data" button that calls the `admin` Edge Function. This lets the admin re-seed without touching the database directly — useful for resets during development.

### Edge Function: game-api (Single Function, Well-Commented)

Single Deno function with internal routing for maintainability. Structure:

```ts
// ── Router ──────────────────────────────────────────────
// Each route maps to a handler function.
// All handlers are in the same file for simplicity.
// ────────────────────────────────────────────────────────

import { serve } from 'https://deno.land/std/http/server.ts'
import { createClient } from 'https://esm.sh/@supabase/supabase-js@2'

serve(async (req) => {
  const url = new URL(req.url)
  const method = req.method

  // ── Route: GET /nations ──
  if (method === 'GET' && url.pathname === '/nations') {
    // ...
  }

  // ── Route: POST /companies ──
  if (method === 'POST' && url.pathname === '/companies') {
    // Deduct 1B from treasury, insert company, return result
    // ...
  }

  // ... etc for all routes
})
```

### Process Turn: Cron-Triggered Edge Function

Supabase Dashboard → Cron → schedule `process-turn` every 5 minutes:
```sql
SELECT cron.schedule(
  'process-turn',
  '*/5 * * * *',
  $$ SELECT net.http_post(
    url:='https://PROJECT.supabase.co/functions/v1/process-turn',
    headers:=jsonb_build_object(
      'Authorization', 'Bearer ' || current_setting('app.settings.service_role_key')
    )
  ) $$
);
```

### Early Turn End: Auto-Process When All Players Submit

After every order submission in `game-api`, check if all players with nations have submitted orders for the current turn. If yes → immediately invoke `process-turn`:

```
order submitted → count players vs submitted orders
                → if all done → POST /process-turn (same as cron trigger)
                → else → wait
```

Three triggers, same idempotent `process-turn` function:

| Trigger | Condition |
|---|---|
| Order submission | All players have submitted |
| Cron (every 5 min) | Deadline has passed |
| Admin button | Manual override |

Players who don't submit by deadline simply miss that turn's orders — their nation gets processed with existing slider settings.

---

### FAQ

**Q: Why one big game-api function instead of many small ones?**
A: Fewer deploys, simpler management, easier to see all routes in one place. The file is well-commented with clear section headers.

**Q: Why not use RLS for everything?**
A: RLS is great for simple reads/ownership checks. Complex business logic (deducting treasury, validating orders, processing combat) needs transactional guarantees that Edge Functions provide with the service role key.

**Q: What happens to existing dev workflow?**
A: After migration, no more `server/` directory. Frontend runs against Supabase directly (`supabase start` for local dev). The Express server is gone.

## Economy (v2) — implemented

### Core Loop
Two separate tax levers incentivize growth in both QoL and companies during peacetime, while allowing crisis-era tax hikes to plug income holes at the cost of long-term damage.

### Income Sources

**QoL Tax** — taxes the population's standard of living:
```
qol_tax_income = BASE_FACTOR × (pop / 40_000_000) × (qol / 50) × qol_tax_rate
```
Where `BASE_FACTOR = 500_000` (scaled for playability, in thousands). Scales linearly with population and QoL.

**Company Tax** — wealth tax on total company valuation:
```
company_tax_income = ∑ (company.profit × company_tax_rate[company_tax_slider])
```
The per-company `tax_rate` column is removed — company tax is determined purely by the national `corporate_tax_level` slider.

Company growth averages ~10%/turn (random 4–16%). Only the corporate tax slider determines how much of the company's value is taxed away.

### Tax Sliders

Two independent sliders replace the old unified tax slider:

**QoL Tax Slider** — taxes population QoL, affects QoL drift:
| Level | Rate | QoL/turn |
|-------|------|----------|
| Very Low | 10% | +2 |
| Low | 25% | +1 |
| Normal | 40% | 0 |
| High | 60% | -2 |
| Very High | 80% | -4 |

**Corporate Tax Slider** — wealth tax on total company valuation, no QoL effect:
| Level | Rate | Net/turn on 22B monopoly | Double | Halve |
|-------|------|--------------------------|--------|-------|
| Very Low | 1% | +1.96B | ~8 turns | — |
| Low | 4% | +1.23B | ~13 turns | — |
| Normal | 8% | +0.26B | ~58 turns | — |
| High | 13% | -0.95B | — | ~16 turns |
| Very High | 17% | -1.91B | — | ~8 turns |

At Very Low the company doubles in ~8 months. At Low it doubles in ~13 months. At Normal growth ≈ tax (~1% net), company stagnates. At High the company halves in ~16 months. At Very High it halves in ~8 months.

Corporate tax is applied on the company's total valuation (stored `profit`), not on growth.

Higher QoL tax = more immediate income but damages QoL (shrinking future QoL tax base). Higher corporate tax = more immediate income but shrinks the private sector (also shrinking future company tax base).

### Civil Spending Slider

| Level | Cost multiplier | Cost formula | QoL/turn |
|-------|----------------|-------------|----------|
| Very Low | 0 | $0 | -1 |
| Low | 1 | `pop × (qol/10) × 1 / 1000` | 0 |
| Normal | 2 | `pop × (qol/10) × 2 / 1000` | +1 |
| High | 3 | `pop × (qol/10) × 3 / 1000` | +2 |
| Very High | 4 | `pop × (qol/10) × 4 / 1000` | +3 |

Civil spending costs money but improves QoL (which grows the future QoL tax base).

### Money Printing Slider

| Level | Cash infusion | Inflation/turn |
|-------|--------------|----------------|
| None | 0% of GDP | 0% |
| Very Low | +0.5% of GDP | +0.5% |
| Low | +1% of GDP | +1% |
| High | +2.5% of GDP | +2.5% |
| Very High | +5% of GDP | +5% |

### Military Sliders (Army / Airforce / Naval)
Effects not yet implemented (future: combat morale modifier). Currently stored on nation row but have no mechanical effect.

### Turn Processing Order (economy.ts)
1. Company profits grow: `newVal = (profit + subsidies) × (1 + growth)` where growth is random 4–16% (avg 10%), **flat** regardless of any slider
2. Corporate wealth tax applied: `tax = newVal × COMPANY_TAX_RATES[corpTaxIdx]` where `COMPANY_TAX_RATES = [0.01, 0.04, 0.08, 0.13, 0.17]`, company stores `newVal - tax`
3. Compute QoL tax = `BASE_FACTOR × (pop/40M) × (qol/50) × TAX_RATES[qolTaxIdx]`
4. Company tax income = `∑ tax` from step 2
5. Compute money printing cash = `GDP × money_printing_rate`
6. Compute civil cost from civil slider
7. `income = qol_tax + company_tax + money_printing_cash`
8. `GDP += income - civil_cost`
9. Deduct unit upkeep from GDP (existing)
10. Advance building units (existing)
11. Apply QoL drift from QoL tax slider + civil slider (QoL tax slider still controls QoL drift; corporate slider has no QoL effect)
12. Record `eco_history` snapshot: gdp, income, inflation, treasury (40% of GDP), qol

### Metrics Tracked in eco_history
- **gdp** — Total cash pool
- **income** — Income generated this turn (for graph)
- **inflation** — Driven by money printing slider
- **treasury** — 40% of GDP (snapshot)
- **qol** — Population quality of life (for graph)

### Policy Change Model
- Changes take effect **immediately** on next turn processing (no drift mechanic in v2).
- Multiple sliders can change in the same turn.

### Deferred (post-v2)
- Military slider morale effects (morale equilibrium, change per turn)
- Incremental policy drift (values drift toward target over several turns)

## Front / Operation System (V2)

### Concept
- A **front** (aka operation) is a military theater between an attacker and a defender — e.g. Iwo Jima, D-Day, Operation Dragoon
- Multiple fronts can exist against the same enemy (D-Day + Dragoon in France)
- Fronts can **merge** after objectives are achieved (e.g. after France is liberated)
- Wars are purely RPS/lore — no mechanical war table; "anyone can apply a front anytime anywhere"

### Flow
1. **Player applies** → creates front with status `pending` (name, target nation, optional lore `war_name`)
2. **Admin verifies** → approves front, sets `max_progress` (pip count) and `front_width` (battles/turn)
3. **Player assigns** formations (divisions/fleets/air groups) to the front
4. **End turn** → battles auto-generate and auto-resolve
5. **Player views results** → scrollable turn-by-turn battle history with combat logs

### Tug-of-War Progress
- Each front has a progress bar with `max_progress` pips (admin-set)
- Attacker wins a frontline battle → progress +1
- Attacker loses → progress -1
- `progress >= max_progress` → attacker wins the front (resolved)
- `progress <= 0` → defender wins the front (resolved)
- A side can **retreat/surrender** at any time, instantly resolving the front
- Island fronts (future): can engage all land units at once; entrenchment modifiers apply

### Front States
| Status | Meaning |
|--------|---------|
| `pending` | Awaiting admin approval |
| `active` | Approved, battles generate each turn |
| `resolved` | Completed (one side won or retreated) |

## Battle Types

### V2: Frontline Battle
- Standard combat on an active front
- Units split into **frontline** (tanks, infantry) and **backline** (arty, AA, engineers)
- Frontline protects backline; if frontline collapses, backline is vulnerable
- Affects the tug-of-war progress (win → +1 pip, loss → -1 pip)

### V3 (deferred)
- **Raid Battle** — in occupied territory, militia/commando only, hits support units
- **Landfall Battle** — naval invasions and airborne landings, support-heavy

## Naval Combat System (V3 — deferred)

### Group-Based Combat
Not per-ship — organized into **groups**:

| Group | Composition | Range | Role |
|-------|-------------|-------|------|
| Carrier Group | 3 carriers | 100km+ | Air projection |
| Line Battle Group | 4 battleships | 40km | Heavy surface combat |
| Cruiser Group | Cruisers | 10-25km | Middle-ground |
| Destroyer Group | Destroyers | 5-10km | Strong attack, short range, screening |
| Submarine | Individual count | Varies | Raiding, stealth attacks |

### Combat Mechanics
- Each group has a **distance** property (range band from enemy)
- Destroyers: strong attack but very limited range (5-10km)
- Cruisers: middle ground (10-25km)
- Battleships: strong attack, long range (40km)
- Carriers: very long range (100km+), limited by plane count and enemy AA
- Each carrier in a group rolls individually to attack
- AA reduces carrier attack effectiveness (e.g. -30%)
- Groups can be targeted individually each "round"

### Future Naval Features
- Convoy battles (commerce raiding)
- Coastal raids (damage units and ships in port)
- Fleet vs fleet engagement system

## Occupation System (V3)

### Occupied Territories
- When a front resolves in the attacker's favor, defender's territory becomes occupied
- Occupied territories can spawn **militia raids** each turn
- Raids draw from a "region deck" — random support battalions in the area become targets
- Occupier can assign formations to garrison duty to reduce raid frequency/severity

### Why Occupation Should Be Expensive
- Militias make occupying powers pay for annexation
- Rewards puppeting over annexation (de jure annexation but de facto autonomy)
- Players can negotiate deals with NPC/player nations to avoid resistance
- Killing population reduces militias but has diplomatic/consequences costs

## Combat Resolution (V2)

### Power Calculation
```
unit_power = (armor_val + firepower_val + speed_val) × (strength / 100)
total_power = sum(all participating units' power)
```

Where stat values: Low=1, Medium=2, High=3.

### Battle Roll
```
attacker_roll = attacker_power × (0.8 + random × 0.4)
defender_roll = defender_power × (0.8 + random × 0.4)
ratio = attacker_roll / defender_roll
```

### Result Determination
| Ratio | Result | Attacker Losses | Defender Losses |
|-------|--------|----------------|-----------------|
| > 1.3 | Attacker win | 10-25% of units | 30-55% of units |
| < 0.7 | Defender win | 30-55% of units | 10-25% of units |
| 0.7–1.3 | Stalemate | 10-25% of units | 10-25% of units |

### Damage Application
- Shuffle units randomly, apply to top X
- Each damaged unit: `new_strength = max(0, strength - 20 - random(0-30))`
- Status: `strength <= 0` → `destroyed`, `< 50` → `damaged`

## Military Turn Processing (V2)

During the turn processing step, the server:
1. For each active front, generate `front_width` frontline battles
2. Resolve all battles (power calc → roll → losses → progress)
3. Update tug-of-war progress for each front
4. Check front resolution (progress extremes, retreat flag)
5. Write battle records with full combat logs
6. Update unit strengths and statuses

### Sector System (Market Caps)

Formula: `cap = (pop / 40M) × (qol / 50) × BASE_CAP × mult`

Multipliers calibrated to match 1930s US economy sector sizes (~$92B GDP, 123M pop):

- Agriculture - 1.0× (US 1930: ~8% of economy)
- Heavy Industry - 1.5× (mining + metals + machinery + construction: ~13%)
- Energy - 1.0× (petroleum, coal, utilities: ~8%)
- Consumer Goods - 1.5× (food processing + textiles + light mfg: ~10%)
- Military & Aerospace - 1.0× (peacetime was ~1%, bumped for wargame relevance)
- Pharmaceuticals - 0.5× (chemicals: ~2%)
- Transport & Trade - 2.5× (transportation + wholesale/retail trade: ~20%)

Formula: `cap = (pop / 40M) × (qol / 50) × 1B × mult`

Example: 100M pop, 50 QoL
- Agriculture (1.0×) = 2.5 × 1B × 1.0 = 2.5B
- Consumer Goods (1.5×) = 2.5 × 1B × 1.5 = 3.75B
- Transport & Trade (2.5×) = 2.5 × 1B × 2.5 = 6.25B

#### Growth Capping (Hard Cap)
- Company profit grows at 1–6% per month (unchanged from current)
- After growth, if sector's total profit exceeds cap, excess is clamped
- Clamped excess redistributed proportionally among companies in the sector

#### Foreign Branches
- `companies` table gets a nullable `parent_nation_id` column
- Foreign branch profit counts toward **host nation's** market cap, but tax flows to **parent nation**
- Lets nations exceed domestic cap by expanding abroad

#### Diversity Bonus (QoL)
- For each sector where total profit ≥ 50% of cap, +1 QoL/turn
- Max bonus = all 7 sectors filled → long-term advantage for diversified economies

#### Company Startup
- Every new company starts with **100M profit** on creation
- Creating a company costs **1B from the nation's treasury** (startup fund deducted on creation)
- Seed nations get 7 pre-existing companies (one per sector), each starting at 100M profit, no treasury cost

#### Seed Data
- Each nation gets 1 company per sector (7 instead of current 3)
- Existing company names map as shown in the table

#### UI

- Per-sector row: sector name, donut chart (untapped vs used cap), total profit / cap
- Expandable list of companies in that sector
- Foreign branches flagged with different color
